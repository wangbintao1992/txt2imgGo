# 金币交易中心 · 需求文档

- 版本：v0.1（基于现有原型逆向整理）
- 来源页面：`http://192.168.8.100:8080/`
- 页面形态：1600 × 720 横版嵌入式 widget，外层为宿主页面，内层为 `srcdoc` iframe
- 当前状态：本地原型，不产生真实支付
- 文档目的：把现有页面整理成可实现、可验收的需求，并标出原型里不完善、需要补的地方

## 1. 产品概述

### 1.1 一句话

给已登录玩家提供一个金币交易中心：玩家之间可以挂单买卖金币，也可以按官方比例充值；卖出所得进入可提现余额，可申请提现到银行卡。

### 1.2 目标用户

- 已有游戏账号、已有金币余额的玩家
- 想把手里的金币卖掉换现金的玩家
- 想用现金或余额补金币的玩家
- 需要查交易记录、提现进度、收款账户的玩家

### 1.3 核心目标

1. **交易闭环**：买、卖、提现、查记录，四件事都能走完。
2. **价格透明**：单价、总价、手续费、实际到账，每一步都算清楚。
3. **资金安全**：余额、冻结、待结算、可提现，四种状态分得清。
4. **合规可控**：实名、年龄、反洗钱、反欺诈、责任游戏、地域限制。
5. **低客服成本**：常见问题在页面内能查到，异常有明确提示。

### 1.4 不在本期范围

- 游戏对局本身
- 金币在游戏内的消耗逻辑
- 支付渠道的具体对接（只定义接口和状态）
- 银行卡/UPI 的真实出款
- 客服后台

### 3.1 购买金币 · 玩家挂单

#### 3.1.1 页面说明

- 标题：购买金币
- 说明：所有玩家挂单均支持部分购买，可按需选择金币数量。
- 标签：交易手续费 0、平台结算。

#### 3.1.2 搜索

- 输入：发布者 ID
- 按钮：搜索
- 规则：
  - 空输入：显示全部
  - 部分匹配：显示匹配行
  - 无匹配：显示空表 + “找到 0 个匹配的发布者”
- 现状：可用。

#### 3.1.3 挂单列表

| 列 | 说明 |
|---|---|
| 发布者 ID | 两位头像 + 完整 ID |
| 出售金币数量 | 卖家当前可售数量 |
| 价格 | 单价，当前统一 `₹1 / 1,000 金币` |
| 订单总价 | 按当前数量算出的总价 |
| 发布时间 | 相对时间，如“刚刚”“1 分钟前” |

规则：

- 点击整行或“购买”打开购买弹窗。
- 列表按发布时间倒序。
- 当前只有 5 条，无分页；生产环境需要分页或虚拟滚动。
- 价格列格式有空格问题：`₹1/ 1,000金币`，应为 `₹1 / 1,000 金币`。

#### 3.1.4 购买订单弹窗

字段：

| 字段 | 说明 |
|---|---|
| 发布者 ID | 卖家 ID + 头像 |
| 可购买 | 状态标签 |
| 购买金币数量 | 可编辑，默认等于卖家可售数量 |
| 卖家最多可售 | 上限提示 |
| 支付方式 | 可提现余额 / 新充值 |
| 金币单价 | 当前单价 |
| 购买金额 | 数量 ÷ 1,000 × 单价 |
| 交易手续费 | 当前 0 |
| 实际支付 | 购买金额 + 手续费 |
| 立即购买 | 主按钮，显示数量 |
| 底部提示 | 成交后金币直接增加到金币余额 |

规则：

- 最小购买量：10,000 金币（当前代码硬编码）。
- 最大购买量：卖家可售数量。
- 数量按 10,000 取整。
- 支付方式默认可提现余额。
- 可提现余额不足时，应阻止提交并提示差额；当前未校验。
- 新充值支付应走支付渠道，成功后金币入账；当前无支付流程。
- 提交前应二次确认卖家 ID、数量、总价；当前弹窗本身就是确认层。
- 提交后应有：处理中、成功、失败、超时、卖家可售不足、价格变动等状态。
- 成功后应刷新余额、挂单列表、交易记录；当前无成功流程。

#### 3.1.5 验收标准

- 输入 9,999：自动归到 10,000，并提示最小购买量。
- 输入超过卖家可售：归到上限，并提示。
- 输入非数字：不崩溃，回到合法值或提示。
- 余额不足：按钮禁用或提交后提示“可提现余额不足，还差 ₹X”。
- 购买成功：金币余额增加，交易记录新增一条“购买”，状态“已完成”。
- 购买失败：不扣款，给出可重试的错误。

### 3.2 购买金币 · 官方充值

#### 3.2.1 档位

| 支付金额 | 获得金币 |
|---:|---:|
| ₹10 | 7,000 |
| ₹30 | 21,000 |
| ₹50 | 35,000 |
| ₹100 | 70,000 |
| ₹200 | 140,000 |
| ₹300 | 210,000 |
| ₹500 | 350,000 |
| ₹1,000 | 700,000 |

比例：`₹1 = 700 金币`。

#### 3.2.2 支付方式

- 新充值支付：走外部支付渠道，金币进入“待打码余额”。
- 可提现余额支付：用已结算余额，金币直接进入可交易余额，无需重复打码。

#### 3.2.3 打码规则

- 新充值获得的金币，需要完成 **2 倍有效下注** 才能解锁出售。
- 例：充 ₹100 得 70,000 金币，需完成 140,000 金币有效下注。
- 余额支付：无需重复打码。

#### 3.2.4 校验

- 余额支付时，支付金额 > 可提现余额：按钮禁用，提示“余额不足，当前可用 ₹X”。
- 新充值支付：不校验余额，走支付渠道。
- 当前实现：余额校验可用；新充值只做展示，不发起真实支付。

#### 3.2.5 验收标准

- 选择档位后，金币数、支付金额、打码要求同步更新。
- 余额不足时不能提交。
- 确认弹窗展示：销售方、官方比例、获得金币、支付金额、支付方式、有效下注要求。
- 成功后：余额或待打码余额增加，交易记录新增“购买”。

### 3.3 出售金币

| 卡片 | 说明 |

| 可发布金币 | 当前可用于挂单的数量 |
| 挂单冻结金币 | 已挂单、未成交的数量，可撤回 |
| 不可出售金币 | 参与对局才能解锁的额度 |

#### 3.3.2 发布卖单

字段：

- 出售金币数量
- “全部”按钮
- 单价：`₹1 / 1,000 金币`
- 交易手续费：0
- 全部成交后获得：`数量 ÷ 1,000` ₹
- 发布卖单按钮

规则：

- 数量必须是 10,000 的整数倍。
- 数量不能超过可发布金币。
- 发布时冻结对应金币；只有实际成交部分才产生销售收入。
- 未成交部分可随时撤回。
- 当前校验：空、非整数、非 10,000 倍数、超过余额。可用。
- 负数输入时，“全部成交后获得”会显示负数，应归零。
- 超过余额且不是 10,000 倍数时，只提示“请输入 10,000 的整数倍”，没有提示余额不足；建议分开展示。

#### 3.3.3 我的挂单

| 字段 | 说明 |
|---|---|
| 订单号 | `S` 开头 |
| 发布时间 | 绝对时间 |
| 剩余 / 原始金币 | 例如 1,200,000 / 2,000,000 |
| 剩余价值 | 剩余金币 ÷ 1,000 |
| 状态 | 部分成交 / 已完成 / 出售中 / 已撤回 |
| 操作 | 撤回剩余 / 无可撤回金币 |

规则：

- 撤回只释放未成交部分，已成交部分不受影响。
- 撤回后：可发布金币增加，挂单剩余归零，状态变“已撤回”，交易记录新增/更新一条“挂单”。
- 当前每页 10 笔，有上一页/下一页。

#### 3.3.4 验收标准

- 10,000 起卖，10,000 整数倍。
- 发布后冻结金币，可发布余额减少。
- 部分成交后，剩余数量和剩余价值正确。
- 撤回后，未成交金币回到可发布余额。
- 已完成挂单不能撤回。

### 3.4 余额与提现

#### 3.4.1 余额卡片

| 卡片 | 说明 |
|---|---|
| 可提现余额 | 已结算，可用于买金币或提现 |
| 提现中 | 已申请、尚未到账的金额，已从可用余额扣除 |

#### 3.4.2 申请提现

字段：

- 提现金额（₹）
- “全部”按钮
- 最低提现：₹300
- 收款账户：银行卡 ···· 2188，可修改
- 交易手续费（3%）
- 每笔固定费用：₹6.00
- 预计到账
- 核对提现按钮

计算：

```
手续费 = 提现金额 × 3% + ₹6
预计到账 = 提现金额 − 手续费
```

规则：

- 最低 ₹300。
- 最多两位小数。
- 不能超过可提现余额。
- 提交前二次确认：申请金额、3% 手续费、固定费用、预计到账、收款账户。
- 提交后：可提现余额减少，提现中增加，交易记录新增“提现”，状态“处理中”。
- 当前校验可用；负数时手续费显示负数，应归零。
- 余额不足时仍显示预计到账，容易误解；建议同时显示“不可提现”原因。

#### 3.4.3 修改收款账户

字段：

- 持卡人姓名
- 银行账号
- IFSC Code
- 手机号码
- 电子邮箱

校验：

- 姓名非空
- 账号 8—20 位数字
- IFSC：`^[A-Z]{4}0[A-Z0-9]{6}$`
- 手机：10 位数字
- 邮箱：标准格式
- 当前校验可用，错误提示统一为“请填写完整且有效的收款账户信息”，建议逐字段提示。

#### 3.4.4 资金使用说明

- 余额买金币：使用可提现余额购买金币，市场交易手续费为 0。
- 金币出售：成交并结算后增加可提现余额；挂单不会直接增加余额。

#### 3.4.5 验收标准

- ₹299 不能提现，提示最低 ₹300。
- ₹300 提现，手续费 ₹15，预计到账 ₹285。
- 超过余额不能提交。
- 修改账户后，卡号后四位更新。
- 提现提交后，余额和提现中数字正确变化。

## 6. 非功能需求

### 6.1 性能

- 首屏 < 1s（内网/原型）；生产环境 < 2s。
- 列表滚动/分页不卡顿。
- 余额、挂单、记录刷新后一致。

### 6.2 安全

- 登录态校验；所有接口鉴权。
- 提现、改银行卡、卖单、购买需要二次验证（密码/OTP）。
- 防 CSRF、防重放、防并发扣款；下单幂等。
- 金额、数量、单价服务端校验，不能只靠前端。
- 敏感信息脱敏：银行卡只显示后四位。
- 操作审计：谁、什么时候、改了什么、IP/设备。
- 风控：同设备多账号、异常高频交易、异常大额、短时间买卖对冲。

### 6.3 合规

- 年龄校验（18+ 或当地法定年龄）。
- KYC/实名认证；大额提现必须完成 KYC。
- AML/反洗钱：交易监控、可疑交易上报、制裁名单筛查。
- 地域限制：按 IP/证件/支付方式限制不可玩地区。
- 责任游戏：限额、冷静期、自我排除。
- 税务：当地税法要求的代扣/申报。
- 支付合规：确认收单行/支付渠道允许该类交易。
- 法务复核：P2P 金币交易、2 倍打码、提现是否构成赌博/类赌博业务。

### 6.4 可访问性

- 键盘可操作：tab 顺序、Enter/Space 触发、Esc 关闭弹窗。
- 焦点管理：弹窗打开后聚焦、关闭后回到触发元素；当前订单弹窗已做，但列表行不可键盘触发。
- `aria-label`、`role=dialog`、`aria-modal`、`aria-live`；当前部分有。
- 对比度、字号、色盲友好；状态不能只靠颜色。

### 6.5 国际化 / 本地化

- 当前 UI 中文，货币 ₹，银行字段 IFSC/HDFC，持卡人 Rahul Kumar，手机号 9876543210。
- 需要明确目标市场：印度？东南亚？中国？
- 货币符号、日期格式、时区、数字格式统一。
- 文案中英混排需要规范。

### 6.6 可观测性

- 前端错误上报、接口耗时、下单成功率、支付成功率、提现失败率。
- 关键链路日志：下单、支付回调、结算、提现、撤回。
- 告警：余额不一致、重复扣款、支付回调丢失、提现积压。

## 8. 不完善之处与风险分析

> 下面按“现状 → 影响 → 建议”写。P0 是上线前必须解决，P1 是体验/一致性，P2 是优化。

### 8.1 P0：交易闭环缺口

1. **玩家购买的“立即购买”按钮没有绑定任何逻辑**
   - 现状：点击无反应，无提示、无扣款、无成功页。
   - 影响：购买主链路走不通，整个“玩家挂单”只是展示。
   - 建议：补提交逻辑、 loading、成功/失败、余额与记录刷新、幂等键。

2. **玩家购买没有余额校验**
   - 现状：余额 ₹428.60，可以选 ₹3,000 的订单，按钮仍可点。
   - 影响：要么产生负余额，要么点击无反应，用户不知道原因。
   - 建议：实时计算差额，按钮禁用 + 文案“还差 ₹X”；服务端再次校验。

3. **玩家购买没有“新充值”支付流程**
   - 现状：可切换“新充值”，但没有支付渠道、回调、失败重试。
   - 影响：选新充值的用户无法完成购买。
   - 建议：接支付网关，定义 pending/success/failed/expired 状态；回调幂等。

4. **个人中心按钮无功能**
   - 现状：点击无反应。
   - 影响：用户找不到实名、安全设置、退出登录。
   - 建议：至少提供账号信息、KYC 状态、修改密码、退出登录。

5. **没有 KYC / 年龄 / 地域 / 责任游戏**
   - 现状：页面只显示用户 ID，没有任何合规门槛。
   - 影响：真钱交易、提现、P2P 金币买卖涉及赌博/类赌博合规风险；可能违反当地法律、支付渠道规则。
   - 建议：上线前做法务复核；补 18+、KYC、AML、地域限制、责任游戏限额。

### 8.2 P0：资金与数据一致性

6. **“可交易金币”口径不清**
   - 现状：顶部 6,060,000；出售页“可发布 6,060,000 + 冻结 1,200,000 + 不可出售 1,000,000 = 8,260,000”。
   - 影响：用户不知道顶部数字是“可用”还是“总额”。
   - 建议：明确四个口径：可用、冻结、待打码、总额；顶部加 tooltip。

7. **待结算、可提现、提现中三个状态没有完整状态机**
   - 现状：出售记录有“待结算”，余额页“提现中 0.00”，但没有结算时间、失败回滚、冻结释放规则。
   - 影响：用户不知道钱什么时候到、失败怎么办。
   - 建议：定义状态机与 SLA；每笔记录展示预计结算时间；失败自动回滚。

8. **提现没有二次验证**
   - 现状：确认弹窗即可提交。
   - 影响：账号被盗后可直接提现/改卡。
   - 建议：提现和改卡要求 OTP/密码；新设备/新卡冷静期；邮件/短信通知。

9. **金额计算只在前端**
   - 现状：单价、手续费、到账都在前端算。
   - 影响：可被篡改；前后端不一致时对账困难。
   - 建议：服务端定价、计费、冻结、结算；前端只做展示。

### 8.3 P1：交互与体验

10. **购买数量输入不严谨**
    - 现状：`type=text`，允许字母、负号、小数点；输入 `1000000.5` 会跳到 3,000,000。
    - 影响：用户困惑，容易误买。
    - 建议：`inputmode=numeric` + 输入过滤 + 明确“最小 10,000，步长 10,000”；非法值给提示，不要静默跳变。

11. **购买弹窗没有确认后的反馈**
    - 现状：没有 loading、成功 toast、失败原因。
    - 影响：用户重复点击。
    - 建议：按钮 loading + 防重复；成功关闭弹窗并刷新；失败保留弹窗并提示。

12. **列表行可点击，但“购买”不是按钮**
    - 现状：`row-action` 是 span；整行 click 打开弹窗；键盘不可触发。
    - 影响：可访问性差；用户不确定点哪里。
    - 建议：改为真正的 `<button>`；行支持 Enter/Space；焦点样式。

13. **相对时间不会更新**
    - 现状：“刚刚”“1 分钟前”是静态文案。
    - 影响：页面停留久了信息失真。
    - 建议：定时刷新或改为绝对时间 + tooltip。

14. **搜索没有空状态和清除按钮**
    - 现状：无匹配时表格空白，只有一行状态文字。
    - 影响：用户以为页面坏了。
    - 建议：空状态插画/文案 + “清除搜索”。

15. **没有排序/筛选**
    - 现状：只能按发布时间看。
    - 影响：大额卖家/低价卖家找不到。
    - 建议：按价格、数量、时间排序；价格区间筛选。

16. **撤回、卖单、提现的“演示”提示不一致**
    - 现状：官方充值写“本地原型 · 不产生真实支付”；卖单/提现确认写“演示”；玩家购买没有任何提示。
    - 影响：用户不知道哪些是真、哪些是假。
    - 建议：统一原型标识；生产环境去掉“演示”，改为真实状态。

17. **客服是静态弹窗**
    - 现状：只有一段说明，没有入口。
    - 影响：用户遇到问题无法求助。
    - 建议：接在线客服/工单/FAQ；记录用户 ID 和最近订单。

### 8.4 P1：文案、格式、本地化

18. **货币符号不统一**
    - 顶部“可提现余额 428.60”没有 `₹`；其他地方有。
    - 建议：统一 `₹428.60`，或全部用 `₹` + 千分位。

19. **价格列格式**
    - `₹1/ 1,000金币` 缺空格，读起来像“1/1000”。
    - 建议：`₹1 / 1,000 金币`。

20. **中英文/印度本地化混用**
    - UI 中文，银行表单是 IFSC/HDFC/Rahul Kumar/印度手机号。
    - 影响：用户不知道这是给哪个市场用的。
    - 建议：明确目标市场；要么全中文+当地银行字段，要么全英文/当地语言；日期、时区、货币统一。

21. **“平台结算”没有解释**
    - 现状：只是一个 badge。
    - 影响：用户不知道平台是否担保、多久结算、出问题找谁。
    - 建议：点击展开说明，或放到交易帮助。

22. **官方价与玩家价的关系没有解释**
    - 现状：官方 ₹1=700，玩家 ₹1=1,000。玩家价更便宜，用户会问为什么还买官方。
    - 影响：转化率低、客服咨询多。
    - 建议：说明差异：官方金币无需打码/更安全/即时到账；玩家金币可能更便宜但有卖家风险/结算时间。

### 8.5 P2：运营与增长

23. **没有新手引导**
    - 建议：首次进入用 3 步引导：选卖家 → 确认数量 → 支付。

24. **没有交易限额/风控提示**
    - 建议：单笔/单日限额；大额交易人工审核；风险提示。

25. **没有通知**
    - 建议：挂单成交、提现到账、价格变动、风控拦截，站内信/推送/邮件。

26. **没有数据看板**
    - 建议：GMV、成交率、平均客单价、提现成功率、客服工单量。

27. **没有 A/B 测试/埋点**
    - 建议：购买漏斗、支付方式选择、官方 vs 玩家转化。

### 8.6 原型 vs 生产

- 当前是本地原型：官方充值明确写“不产生真实支付”，卖单/提现确认写“演示”。
- 生产环境必须补：真实登录、服务端定价、支付、结算、KYC、风控、审计、客服、监控。
- 不要直接把原型当生产：前端计算、无鉴权、无幂等、无状态机，都是上线阻断项。

### 8.7 功能冲突清单

> 这一节只列“两个功能互相打架”的地方。最大的一条是：页面同时像 P2P 市场，又像平台回购，产品模型没定。

| # | 冲突 | 现状 | 影响 | 建议 |
|---|---|---|---|---|
| C1 | 官方价 vs 玩家价 | 官方 ₹1=700，玩家 ₹1=1,000 | 玩家市场更便宜，官方档位没有购买理由 | 说明官方金币的差异：无打码、无卖家风险、即时到账、可开票 |
| C2 | 2 倍打码只约束新充值 | 玩家买入的金币没有说明是否打码 | 可以绕开打码：买玩家币 → 对局 → 卖 | 明确玩家买入币的可售规则；风控识别套利 |
| C3 | 新充值金币归属 | 官方页说进“待打码余额”；购买弹窗说“直接增加到金币余额” | 用户不知道能不能马上卖 | 统一余额桶和文案 |
| C4 | “可交易金币”用途 | 头部 6,060,000，但购买只支持现金/新充值 | 用户以为能用金币买金币 | 改名“可出售金币”，或增加金币支付 |
| C5 | 余额口径 | 6,060,000 + 1,200,000 + 1,000,000 = 8,260,000 | 用户不知道总额 | 分开展示可用/冻结/待打码/总额 |
| C6 | 待结算不可见 | 出售 +800 待结算，钱包只显示可提现/提现中 | 用户不知道 800 何时到 | 增加“待结算”卡片和预计到账时间 |
| C7 | 平台结算 vs P2P | 有“平台结算”badge，又要求核对发布者 ID | 用户不知道谁担保、出纠纷找谁 | 明确托管/担保/纠纷流程；补卖家信用 |
| C8 | P2P 还是平台定价 | 有发布者 ID，但卖单价格固定 ₹1/1,000，不能自定价 | 不是真正 P2P；卖家没有定价权 | 二选一：真 P2P（卖家定价）或平台回购（去掉卖家 ID） |
| C9 | 官方页仍显示玩家价 | 官方充值页侧栏仍是“玩家市场单价” | 一屏两个价格 | 官方页切换侧栏价格或隐藏 |
| C10 | 订单总价 vs 部分购买 | 列表“订单总价”是整单，弹窗可部分买 | 用户以为必须买整单 | 改“整单参考总价” |
| C11 | 购买按钮不是按钮 | 整行可点，操作列是 span | 键盘不可用、误点 | 改真 `<button>`，行支持 Enter/Space |
| C12 | 状态命名 | 出售中/挂单中；不可出售/待打码 | 同一状态多个名字 | 建统一状态字典 |
| C13 | 演示标识 | 官方页“本地原型”，卖/提“演示”，买无 | 用户不知道真假 | 统一原型标识 |
| C14 | 手续费语义 | 市场交易手续费 0，提现有 3%+6 | 用户以为全免 | 区分“交易费”和“提现费” |
| C15 | 订单号/账本 | 挂单 S、成交 S、撤回 C；列表和成交混 | 对账困难 | 统一 ID 规则和关联字段 |

| C18 | 个人中心 | 按钮无功能 | 用户找不到实名/安全 | 实现或移除 |

### 8.8 漏洞清单

> 当前是本地原型，部分“漏洞”是演示逻辑。下面标了“原型”的，意思是：演示可以，但这段逻辑不能原样上线。

| # | 漏洞 | 位置/证据 | 影响 | 建议 |
|---|---|---|---|---|
| V1 | 新充值不付款就加币（原型） | `official-buy` 的 `else { locked += coins; turnoverLeft += coins*2; }` | 若原样上线，等于免费发币 | 必须等支付回调；先 pending，回调成功再入账 |
| V2 | 金额只在前端算 | `renderOrder`、`calculateSell`、`calculateWithdrawal`、`renderOfficial` | 改价、改余额、负数、并发 | 服务端定价/计费/校验；前端只展示 |
| V3 | 无鉴权、CSRF、幂等 | 页面无登录态、token、idempotency key | 越权、重复下单、重放 | 登录态、CSRF、幂等键、限流 |
| V4 | 提现/改卡无 2FA | 确认弹窗即提交 | 账号被盗后可提现/改卡 | OTP/密码、新卡冷静期、短信/邮件通知 |
| V5 | 存储型 XSS | `detail()`、`renderListings`、`renderHistory` 用 `innerHTML` 拼 `r.note`、`r.id`、`l.status` 等 | 恶意备注/ID 可执行脚本 | 输出编码；用 `textContent` 或转义 |
| V6 | 小数输入被拼接 | `coinInput.value.replace(/[^0-9]/g,'')`；`1000000.5` → `10000005` → 上限 | 误买最大额 | 严格解析；拒绝非法字符；明确提示 |
| V7 | 售罄仍可买 | `Math.max(10000, Math.min(quantity, max))`，`max=0` 时仍得 10,000 | 下单到无货卖家 | `max<=0` 禁用/下架 |
| V8 | 选中卖家回退不更新 | `selectedSeller` 不存在时 `selectedRow()` 回退 `rows[0]` | 可能下到错误卖家 | 回退时同步 `selectedSeller` |
| V9 | 重复订单号 | `serial` 内存自增，刷新重置 | ID 冲突、对账错 | 服务端序列/UUID |
| V10 | 余额/挂单只在内存 | `available/cash/listings/records` 变量 | 刷新丢失、可篡改 | 服务端持久化 + 审计 |
| V11 | 银行卡全量回填 | 编辑表单 `value="000000002188"` | 敏感信息暴露 | 掩码、重新输入、OTP |
| V12 | `privateContent` 未校验 | `saved.quantity/payment/selectedSeller` | 状态篡改、错误订单 | 白名单/范围校验 |
| V13 | 无审计/对账 | 没有 ledger、没有双录 | 资金争议查不清 | 流水、双录、日对账 |
| V14 | iframe 沙箱 | 当前 `sandbox="allow-scripts"`（没有 `allow-same-origin`，是好的） | 若误加 `allow-same-origin` 可越权 | 保持最小权限、CSP、`frame-ancestors` |

### 8.9 一句话总结

- **功能冲突**：产品模型没定死——是 P2P 还是平台回购；价格、打码、结算、卖家身份四件事互相打架。
- **功能漏洞**：玩家购买主按钮没逻辑；新充值支付没闭环；个人中心没实现；余额/挂单/记录不持久。
- **安全漏洞**：前端算钱、无鉴权/幂等/2FA、`innerHTML` XSS、银行卡全量回填；其中 V1 是原型演示逻辑，不能原样上线。

## 9. 建议迭代顺序

### 第一阶段：交易闭环（P0）

1. 玩家购买提交 + 余额校验 + 成功/失败 + 刷新。
2. 服务端定价/计费/冻结/结算。
3. 订单状态机 + 幂等 + 对账。
4. 提现二次验证 + 改卡冷静期。
5. KYC/年龄/地域/责任游戏合规评审。

### 第二阶段：体验与一致性（P1）

6. 输入校验、空状态、loading、错误提示。
7. 列表排序/筛选/分页。
8. 统一货币/日期/文案/原型标识。
9. 可访问性：键盘、焦点、aria。
10. 客服/FAQ/工单。

### 第三阶段：运营与增长（P2）

11. 通知、埋点、数据看板。
12. 新手引导、限额、风控规则。
13. 多语言/多市场。

## 11. 业务确认问题（资金、打码、手续费）

> 这一节不是 UI 问题，是“钱怎么算、怎么锁、怎么解锁”的业务规则。现有页面只有“可交易金币 / 挂单冻结 / 不可出售 / 可提现 / 提现中”五个桶，但没定义来源和转换。下面先把桶补齐，再问问题。

### 11.1 先定钱包模型

建议至少分八个桶：

**金币桶**

- K1 可交易金币：可卖、可玩
- K2 不可出售金币：可玩，不可卖；完成打码后转 K1
- K3 挂单冻结：挂单中，不可玩、不可卖
- K4 对局冻结：下注中，不可用

**现金桶**

- C1 可提现余额：可提现、可买币
- C2 不可提现余额：可买币、可玩，不可直接提现；完成打码后转 C1
- C3 提现中：已申请，不可用
- C4 待结算：卖出待结算，未进 C1

**问题 1**：这八个桶是不是最终模型？还是“可交易金币”和“可提现余额”其实是一个桶的两种展示？

### 11.2 资金来源 → 进哪个桶

| 资金来源 | 进哪个桶 | 可提现 | 可卖 | 需要打码 |
|---|---|---|---|---|
| 官方充值（新充值） | K2 | 否 | 否 | 2x |
| 官方充值（可提现余额支付） | K1 | 是 | 是 | 否 |
| 玩家市场买入（可提现余额支付） | K1？ | ？ | ？ | ？ |
| 玩家市场买入（新充值支付） | K2？ | ？ | ？ | ？ |
| 对局赢的金币（用 K1 下注） | K1 | 是 | 是 | 否 |
| 对局赢的金币（用 K2 下注） | K2？ | ？ | ？ | ？ |
| 卖出 K1 所得 | C1 | 是 | — | 否 |
| 卖出 K2 所得 | C2？ | ？ | — | ？ |
| 活动/补偿/返水 | C2 或 K2 | 否 | 否 | ？ |
| 提现失败退回 | C1 | 是 | — | 否 |
| chargeback/拒付 | 负 C1？ | — | — | — |

**问题 2**：玩家市场买入的金币，是 K1 还是 K2？如果买家用“可提现余额”支付，卖家收到 C1，买家拿到的金币如果直接是 K1，就可以立刻再卖，形成“零成本倒手”。这是套利还是允许？

**问题 3**：用 K2 下注赢来的金币，是 K1 还是 K2？如果赢来的是 K1，用户可以用 K2 下注，赢了就变可提现，2 倍打码被绕过。建议 K2 下注的赢利也进 K2，按比例解锁。

### 11.3 2 倍有效下注怎么算

现有玩法：组局、赛事、匹配。建议定义：

> 有效下注额 = Σ（本人实际投入的、已完成对局的、可计入的筹码）

不计入：

- 平台抽水/服务费
- 奖金、返水、赠送筹码
- 未开始/取消/退款的对局
- 观战、练习、人机
- 自己跟自己、同设备/同 IP 多账号
- 未实际承担风险的筹码（例如还没下注就弃牌）

计入比例建议：

| 玩法 | 计入比例 | 原因 |
|---|---:|---|
| 匹配（现金桌） | 100% | 标准对局，风险真实 |
| 赛事（锦标赛） | 100%（只算买入，不算手续费） | 买入即风险 |
| 组局（私人房） | 0%—50% | 容易串通、故意输赢，建议 0% 或限额 |
| 人机/练习 | 0% | 无真实风险 |
| 观战 | 0% | 无下注 |

**问题 4**：这个公式是否认可？特别是“组局”要不要计入？如果计入，如何防止两个人互相故意输赢来刷流水？

**问题 5**：赛事只算买入，还是算“买入 + 再买入 + 加购”？再买入/加购是否计入？手续费是否排除？

**问题 6**：现金桌的“有效下注”是算“底注+盲注+每次下注”，还是算“最终底池”？建议算本人实际投入的筹码，不算对手投入，不算抽水。

**问题 7**：弃牌前的下注算不算？例如翻牌前下注 1,000 后弃牌，这 1,000 算不算？建议算，因为已经承担风险。

**问题 8**：平局/退款/断线自动弃牌算不算？建议正常结算的平局算；取消/退款不算；断线但盲注已投入的算。

**问题 9**：同一笔金币反复下注，是否重复计入？例如 1,000 金币下注、赢回 1,000、再下注 1,000，流水是 2,000 还是 1,000？建议按“每次实际投入”累计算 2,000，但要防风控刷流水。

**问题 10**：2 倍是“充值金币的 2 倍”还是“充值金额的 2 倍等值金币”？现有页面写 140,000 金币，按金币。

**问题 11**：打码进度按“总流水”还是“净流水”？建议总流水，不是净赢。

**问题 12**：多笔充值、不同打码要求，怎么合并？建议 FIFO：先完成的先解锁；或按比例释放。

**问题 13**：打码完成后，解锁的是“本金”还是“本金+赢利”？建议只解锁充值本金对应的 K2；赢利按 11.2 的规则。

**问题 14**：打码期间，用户能不能卖 K1、提现 C1？建议可以，但 K1/C1 不能用来“替” K2 完成打码；否则用户拿可提现的钱去玩，解锁 K2，再把 K2 卖掉。

### 11.4 出售手续费

现状：玩家市场手续费 0。需要确认：

**问题 15**：0 手续费是永久策略还是拉新期？如果是永久，平台从哪里赚钱？官方 1:700 的价差是否足以覆盖支付、客服、风控、提现成本？

**问题 16**：如果收手续费，向谁收？

- A. 卖家：从卖出所得扣 1%—3%
- B. 买家：在成交价上加 1%—2%
- C. 双边：maker/taker
- D. 平台价差：平台 1:950 买、1:1000 卖，不显性收费

建议优先 D，用户感知低；或 A，透明。

**问题 17**：手续费有没有下限/上限？例如最低 ₹1，最高 ₹50。小额卖单 10,000 金币 = ₹10，1% 只有 ₹0.10，不够支付通道成本。

**问题 18**：手续费是否含税？GST/服务税怎么开票？

**问题 19**：提现费 3%+6 和出售费是否叠加？如果卖家卖 10,000 金币得 ₹10，再提现，3%+6 会超过本金；需要设最低提现和费率上限。

**问题 20**：部分成交时，手续费按每笔成交收，还是按整个挂单收？建议按每笔成交收。

**问题 21**：撤单/未成交是否收费？建议不收费。

### 11.5 卖出所得：可提现还是不可提现

这是最关键的问题。

**问题 22**：卖出 K1 所得，进 C1 还是 C2？

- 进 C1：卖家体验好，但等于开放现金提现，AML/RMT 风险高。
- 进 C2：需要再打码才能提现，合规更稳，但卖家可能不接受。
- 按来源：K1 来源干净就进 C1；K2 解锁后卖出进 C2 或 C1？建议按来源。

**问题 23**：卖出 K2（完成打码后解锁）所得，进 C1 还是 C2？如果进 C1，打码完成后就完全可提现；如果进 C2，还需要再打码，用户会觉得被“二次打码”。建议 K2 完成打码后转 K1，卖出进 C1，但设提现限额/风控。

**问题 24**：如果卖出所得进 C2，C2 能不能买币？能不能玩？能不能转给 C1？转换比例/打码要求是什么？

**问题 25**：如果 C2 不够支付某笔购买/费用，是否自动扣 C1？

- 建议：不自动跨桶。购买时让用户选择支付桶；如果 C2 不足，提示“不可提现余额不足，是否使用可提现余额”，用户确认后才扣 C1。
- 如果是费用/拒付/罚款，定义优先级：先 C2，再 C1，再负余额，并通知用户。

**问题 26**：提现时只用 C1，还是 C1+C2 都可以？如果 C2 不能提现，页面必须明确展示“不可提现余额”，否则用户会以为 428.60 是全部。

**问题 27**：C1 和 C2 之间有没有“转换”入口？如果有，转换比例、手续费、打码要求、每日限额是什么？建议只允许 C2→C1（完成打码），不允许 C1→C2，除非用户明确购买不可提现的优惠币。

**问题 28**：C2 有没有有效期？过期作废还是回收？如果过期，用户会投诉；建议至少 30 天，提前通知。

**问题 29**：卖出所得 C1 能不能直接再买 K1，形成“卖→买→卖”循环？如果可以，0 手续费下没有套利，但会刷交易量/返水；如果平台有返水/活动，可能被刷。建议限制自买自卖、同设备多账号、短时间循环。

**问题 30**：如果买家拒付/chargeback，卖家已经提现，平台怎么办？建议卖家所得有 T+N 冻结期；拒付时从冻结/未来所得扣回；不足则负余额。

### 11.6 余额不足的扣款顺序

**问题 31**：用户下单/买入时，默认扣哪个桶？建议先 K2（如果能用于购买）→ K1 → C2 → C1；或让用户选。但“金币买金币”本身产品上是否允许？现有页面只允许现金/新充值买币，金币不能买币。

**问题 32**：用户提现时，C1 不足但 C2 足够，是否允许“C2 转 C1 再提现”？如果不允许，提示“可提现余额不足”；如果允许，按什么打码/手续费？

**问题 33**：用户对局亏损，扣哪个桶？建议按下注来源扣；如果混合下注，按比例扣。不能自动用 C1 补 K2 的亏损。

**问题 34**：用户被罚款/扣回奖励，C2 不足时是否扣 C1？建议先 C2，再 C1，再负余额；必须通知并给申诉入口。

**问题 35**：负余额怎么处理？是否允许继续玩？是否从后续充值/赢利扣？是否限制提现？

### 11.9 建议的最小可行规则（供拍板）

如果现在要定一版，建议：

1. 金币分 K1（可卖）/ K2（不可卖，2x 解锁）/ K3（冻结）。
2. 现金分 C1（可提现）/ C2（不可提现）/ C3（提现中）/ C4（待结算）。
3. 新充值 → K2；K2 完成 2x 有效下注 → K1。
4. 有效下注只算匹配和赛事的本人实际投入；组局 0%（或 50% + 限额）；人机/观战/取消/退款不算。
5. 玩家市场买入：用 C1 支付 → K1；用新充值支付 → K2。
6. 卖出 K1 → C1；卖出 K2（解锁后）→ C1，但设 T+1 冻结和提现限额。
7. 出售手续费先按 0，但保留提现费 3%+6；如果平台需要收入，优先用官方价差，不建议双边收费。
8. C2 不足时不自动扣 C1；购买时让用户选桶，费用/拒付才按 C2→C1→负余额扣。
9. 所有转换、扣款、解锁写 ledger，可审计。
